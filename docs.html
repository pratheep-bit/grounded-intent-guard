Verification Steps

6-Step Wiring & Verification Runbook

Execute each command in sequence to verify all components of Grounded Intent Guard on your machine.

STEP 1 Sanity-test impact vector in isolation (No deletion occurs)

Tests that compute_impact_vector() accurately evaluates physical file targets without actually deleting anything.

bash — step-1.sh 
$ mkdir -p /tmp/demo && echo "hi" > /tmp/demo/a.txt
$ python3 guard_engine.py rm -rf /tmp/demo
Expected Behavior:
Silence with exit code 0 (tiny 1-file target under 0.30 WARN threshold) or a clean risk assessment explaining the impact.
STEP 2 Sanity-test git-grounded impact (Flagship Test)

The core differentiator: git reset --hard names no explicit paths, but Grounded Intent Guard inspects git porcelain status to ground uncommitted work loss.

bash — step-2-git-test.sh 
# 1. Initialize a test repository with initial commit
$ mkdir -p /tmp/demogit && cd /tmp/demogit
$ git init -q -b main && git config user.email "a@a.com" && git config user.name "a"
$ echo "one" > a.txt && git add -A && git commit -qm "init"

# 2. Add uncommitted changes to create uncommitted dirty state
$ echo "two" >> a.txt

# 3. Test destructive git reset interception
$ python3 /Users/pratheepselvam/Documents/kernal/guard_engine.py git reset --hard
Expected Behavior:
Triggers a WARN or CONFIRM explanation mentioning uncommitted git changes and calculating 0.20 recoverability, even without any path argument.
STEP 3 Sanity-test trajectory drift logging

Tests non-blocking category recording via --log-only without executing full checks.

bash — step-3-drift.sh 
$ python3 guard_engine.py --log-only "ls -la" && cat /tmp/guard_session.json
Expected Behavior:
Outputs a valid JSON state containing {"window": ["OTHER"]} in the session file.
STEP 4 Source shell integration into interactive shell

Spawns an interactive shell with guard.sh loaded and tests interactive abortion (`n` at confirm prompt).

bash — step-4-shell.sh 
# Start an interactive subshell with guard.sh sourced
$ bash --rcfile <(echo 'source /Users/pratheepselvam/Documents/kernal/guard.sh')

# Create test targets and test interactive prompt
guard$ mkdir -p /tmp/demo_folder && touch /tmp/demo_folder/data.bin
guard$ rm -rf /tmp/demo_folder
# -> Type 'n' to abort deletion when prompted
guard$ ls -d /tmp/demo_folder  # Verify folder is preserved!
Expected Behavior:
Guard prompts [guard] Proceed with this DELETE anyway? [y/N]. Entering n aborts execution with exit code 1; ls confirms files remain intact.
STEP 5 Confirm DEBUG trap doesn't double-log guarded commands

Ensures that guarded commands wrapped by shell functions are logged once by the wrapper, and not duplicated by the DEBUG trap.

bash — step-5-trap-check.sh 
$ touch /tmp/throwaway.txt && rm /tmp/throwaway.txt
$ ls -la /tmp
$ cat /tmp/guard_session.json
Expected Behavior:
The session window contains exactly one DELETE entry and one OTHER entry (no double-counting).
STEP 6 Rehearse the known bypass (Disclosed Limitation)

Verify the documented bypass mechanism using backslash escape (\rm) or absolute path (/bin/rm).

bash — step-6-bypass.sh 
$ touch /tmp/bypass_test.txt
$ \rm /tmp/bypass_test.txt  # Or: /bin/rm /tmp/bypass_test.txt
Expected Behavior:
Deletes instantly without guard interception. This confirms that shell-function wrapping operates in user space and discloses the design boundary.

Disclosed Limitations & Threat Model

Honest, transparent architectural disclosures. What Grounded Intent Guard does and does not protect against.

1. Bypassable By Design (User Space Wrapping)

Function wrapping is bypassed by escaped names (\rm), full binary paths (/bin/rm), or non-interactive bash scripts that don't source guard.sh. It is a pre-execution safety layer for human error and interactive shell workflows, not a kernel-level sandbox (e.g. eBPF/LSM).

2. Scoped to File-Centric Risk Models

Intentionally scoped to commands whose danger is represented by a filesystem impact vector (files, bytes, git tree, mount boundaries). Commands like kill, docker rm, or kubectl delete require process state or dependency graph models not built into this MVP.

3. Snapshot Capability Is Stubbed

snapshot_available() currently returns False by default. In production environments, it can be wired to btrfs subvolume list or ZFS snapshots to credit automated rollbacks in the recoverability calculation.

4. Deep Tree Walking Scale

Directory targets are traversed using standard os.walk(). For extremely massive mono-repos (100k+ files), a statistical sampling approach (walk 2,000 files and extrapolate) can be enabled to maintain sub-5ms evaluation latency.

Configuration Guide

Constants & Tunables Reference

All constants are declared at the top of guard_engine.py and can be calibrated for your workload.

Constant Default Value Description Recommended Tuning
SESSION_FILE /tmp/guard_session.json Location for rolling trajectory history window Move to $XDG_RUNTIME_DIR for multi-user safety
WINDOW_SIZE 12 Number of recent commands feeding drift computation Set between 8 (fast context switch) and 20 (longer memory)
RISK_THRESHOLDS {"WARN": 0.3, "CONFIRM": 0.55, "BLOCK": 0.8} Score cutoffs mapping to friction tiers Adjust in Calibration Lab based on team risk appetite
RISK_WEIGHTS {"impact": 0.45, "drift": 0.25, "irreversibility": 0.30} Relative weight of signals in composite score Must sum to 1.0 (impact dominates data loss)
CATEGORY_RULES DELETE, OVERWRITE, PERMISSION, MOVE Mapping of commands to category types Extend to intercept additional file-centric commands
